# 论文吸收（终稿 → 结构化 → 补工厂）

> **本文只负责**：只有终稿论文、没有开题时，工厂怎么**吸收**「能生成包的要素」、入库结构、入库后**覆盖判断**（已齐 / 差皮 / 差域）、喂助手、验收、控制台 UI 定稿；以及**同材同果**（同材料反复上传结果一致）纪律。  
> **不负责**：按论文直接 bake 出 ZIP；把论文当开题去撞现网匹配；论文排版/出图几何（见 [`thesis-diagram-export.md`](./thesis-diagram-export.md)、parked **m**）；开题对齐门禁本身（见 [`opening-align-gate.md`](./opening-align-gate.md)）。  
> **状态**：厂库 / 控制台已落地 · 2026-11-21；**分块抽取按 §3 已重写**（`EXTRACTOR_VERSION`≥20 · 2026-11-22）：P1 设计主矿 / P2 需求定角色 / P3 仅佐证；图侧接 PyMuPDF+pdfplumber（OCR 可选）。**表结构→`draft_schema_sql` 落库**（≥42 · 2026-11-23）：**L1 正文主矿**（题注/`（n）××表 en…如表所示` + 类型词锚定切列；表头/中文·Oracle 类型/TSV/括号题注/词界防误切）；L2 pdfplumber 仅补空；材料有而抽空=工厂漏挖；**不**写进学生 ZIP。  
> **索引**：[README.md](./README.md) · 换皮施工 [`domain-skin-onboarding.md`](./domain-skin-onboarding.md) · LLM 原则 [`llm-determinism.md`](./llm-determinism.md)

## 0. 人话口径（定死）

1. 手里**只有终稿论文**，没有开题。  
2. **上传论文不是为了出包**，是从里面吸收「能生成包的要素」。  
3. **不要像开题那样去撞现有匹配**——论文叙事和开题材料本来就不对齐，硬撞一定配不完美。  
4. 抽完进**厂库记录**（见 §4.2），结构就是开题那份 **`proposal` 摘要**（同名同物）。**无论现网能不能盖住，前半截吸收都要做。**  
5. 入库之后才做**覆盖判断**（§2.1）：已齐 / 差皮 / 差域——这决定喂助手干什么，**不是**上传瞬间的 `project_match`。  
6. **能盖住 ≠ 白吸**：仍要结构化存档 +（通常）第 2 刀回归证明；喂助手稿写明「以验证为主，勿新开域」。  
7. **盖不住**才走补厂主路径（补皮 / 挂 cap / 薄开 `DOM-*`）；见 onboarding。  
8. **选题年份不能照搬**；题名可存档对照，**不当**喂助手 / 反推开题的默认正文源。  
9. **格式参考**可另路使用（章节骨架、图种、题注），不挡本主线，也不驱动匹配。  
10. **按标题语义分块抽**（§3）：**总体设计·各端模块**是功能主矿；**需求/用例**定角色；实现/测试只佐证；目录/技术章/可行性/结论致谢文献丢掉；章号不固定。  
11. **验收**看工厂能不能交（已齐则证明仍交；有缺口则补完再交），不审学生有没有撒谎。  
12. 控制台三个「论文」词必须切开（见 §1.1）；吸收页**禁止**出现建项 / 匹配 / 出包主按钮。  
13. **一刻不当永久**（§2.2）：同一条厂库记录可反复重抽、改结构、改覆盖、再喂助手、再验收；`covered`/`patched`/`fed` 都是当前看法，不是封档。  
14. **同材同果**（§2.3，本册说的防幻觉）：**同一份材料**前后上传 / 重抽，抽出来的 `proposal` **必须一致**，不能每次飘一版；禁止靠非确定性模型让「点一下结果变一下」。  
15. **口令按完整产品交**（§8.7 / §9）：`做论文吸收` **不是 MVP、不是半截入口**；表/API/页/迭代/同材同果测/Help 一次交齐可运营用的功能。

一句话：

**吸收 = 同一材料得到同一说明书进厂库；人改覆盖/结构才变；补厂只补真缺口——迭代改的是判断与工厂，不是同文件抽两次抽成两套故事。实现时交产品功能，不交演示壳。**

## 1. 和「上传开题」差在哪

| | 开题 / 任务书等材料 | 终稿论文 |
|---|---|---|
| 目的 | 匹配 → bake → 出包 | **吸收 → 入库 → 覆盖判断 →（有缺口才）补工厂** |
| 撞现有 `DOM-*` 匹配 | 要尽量准（出包合同） | **禁止**上传瞬间硬配；入库后只做覆盖判断（§2.1） |
| 成功态 | 可预览 / 可出 ZIP | **`proposal` 进厂库**；已齐则回归证明，有缺口则补齐后再验 |
| 控制台落点 | `/projects` 上传分堆 | **独立** `/thesis-absorb`（资产台侧栏） |
| 共同点 | 都在挖「能生成包的要素」 | 同左 |

控制台文案必须写死「吸收进厂 / 补能力」，禁止和「上传开题出包」共用一个含糊入口。

### 1.1 三个「论文」词（命名隔离）

| 叫法 | 是什么 | 不是什么 |
|------|--------|----------|
| **终稿吸收** / **论文进厂**（本册） | 吃终稿（§3：设计主矿 + 需求定角色 + 实现/测试佐证）→ 厂库 → 覆盖判断 → 有缺口才补厂 | 不是出包、不是 bake 出图；已齐也要吸 |
| **产物 → 论文材料**（项目详情） | 已 bake 工程推导的模块图/类图等 | 不是上传终稿 |
| **格式参考**（§7 旁路） | 章节骨架、图种、题注习惯 | 不驱动匹配、不替代吸收主线 |

侧栏 / 面包屑 / Help **禁止**把本册入口写成「论文材料」（会与产物轨撞车）。推荐标签：**终稿吸收**；副文：**抽需求·设计·实现进厂库，不建项**。

## 2. 主链路

```
终稿 PDF/Word
    ↓  抽取（不匹配、不 bake）
结构化「可交能力要素」→ 厂库记录（持有 proposal）   ← 前半截总做
    ↓  覆盖判断（§2.1，人+助手对照现网 DOM/皮/cap）
    ├─ 已齐  → 喂助手稿标「验证/回归」；可直接第 2 刀证明；status→covered
    ├─ 差皮  → 只补皮（rules/pack/seed 同到）
    └─ 差域/能力 → 挂 cap 或薄开 DOM-*（onboarding）
    ↓  验收（第 2 刀可选、与吸收记录解耦）
结构 → 能否反推开题写法（第 1 刀）
结构 → 反推开题 txt → 现网「项目」页试匹配+bake（第 2 刀，非交货）
```

补厂落点走现有工序：见 [`domain-skin-onboarding.md`](./domain-skin-onboarding.md)。  
**禁止**只擦当面学生 ZIP；要素按类去重进厂，一篇论文 ≠ 永久独占一条平行逻辑。

### 2.1 覆盖判断（入库之后，不是上传硬匹配）

人话里的「能和现有域/皮匹配上」= **现厂已经盖住这篇实现章的主路径**；  
「匹配不上」= **有缺口要补**。两端都走本册，差别只在入库**之后**的动作。

| 判断 | 何时 | 吸收还做吗 | 喂助手默认任务 | 验收侧重 |
|------|------|------------|----------------|----------|
| **已齐** | 某 `DOM-*`（及现皮）已能演示实现章主路径；可见面/种子不挡答辩 | **做**（结构化存档 + 可作回归样本） | **验证**：对照 gap 册确认无需新开；可跑第 2 刀；**禁止**借机新开平行域 | 第 2 刀证明「现厂已交」为主 |
| **差皮** | 主流程壳已有，但行业词/种子/眉标/分类轴不对 | **做** | **只补皮**（P1～P10）；能皮就皮 | 补皮后再第 2 刀 |
| **差域/能力** | 主流程盖不住，或缺必备 cap | **做** | **挂 cap / 薄开 DOM-***；禁止只擦 ZIP、禁止平行旁路 | 补厂后再第 2 刀 |

纪律：

1. **上传 / 抽取瞬间禁止**跑 `proposal_match` / 写入 `hits`·`domain` 当「已匹配出包结果」。  
2. 覆盖判断是**对照说明书看现厂**，结论可写在记录的提案字段（如人工选的挂靠 `domain` 草稿、缺口列表），文案必须是「覆盖提案 / 缺口」，不是「匹配成功可下载」。  
3. **已齐不是失败**：本册不是「只有配不上才吸收」；配得上则少干活，但说明书仍进厂库。  
4. 拿不准时默认按 **差皮或差域** 走助手审，不要假装已齐。  
5. 覆盖结论可随时改（工厂补完、第 2 刀翻车、结构重抽后）——见 §2.2，**禁止**「标过已齐就锁死」。

### 2.2 迭代工作件（一刻不当永久）

本能力按**可反复迭代的工作件**做，不按「上传一次 → 抽一次 → 喂一次 → 结束」的典礼做。

| 可反复做的事 | 口径 |
|--------------|------|
| **重抽** | 同 `id` 再跑裁切+`summarize`（换规则、换文件、补图后再抽都行）；`extract_round` +1；当前 `proposal` 被新结果替换（可不做历史表，但**必须**能重抽且同材同果） |
| **改结构** | 人可勾选/增删 `feature_lines`、改 `out_scope_lines`、改切片；改完可再喂、再判覆盖 |
| **改覆盖** | `unknown` ↔ `covered` ↔ `skin_gap` ↔ `domain_gap` 任意重标；工厂演进后昨天「差域」今天可能「已齐」 |
| **再喂助手** | 每次按**当前** `proposal` + **当前** `coverage` 拼稿；`fed` 只表示「曾导出过」，不禁止再复制 |
| **再验收** | 第 1 / 2 刀可多次；第 2 刀红了 → 改覆盖或改结构，不是删记录重开典礼 |
| **重开状态** | `covered` / `patched` / `fed` → 一改结构或重抽，应回到可工作态（如 `review` / `stored`），文案「需再确认覆盖」，**不要**灰掉整页只读封档 |

纪律：

1. **默认同一条记录上迭代**；不要每点一次「重新抽取」就新建一行（除非运营明确「另存为新篇」）。  
2. **状态不是单向葬礼**：终端态只是标签；按钮「重新抽取 / 改覆盖 / 再复制喂助手稿」在已齐、已补厂后仍可用。  
3. **空抽告警随当前稿**：重抽变厚 → 警告消失；人删瘦了 → 警告可再出现。  
4. **补厂进度在工厂侧**（域皮/测例/gap 册）；吸收记录不假装「补完就永不回头」——现厂变了，同一说明书还要能再对照。  
5. 做表/API/UI 时按上表验收；若做成一次性流水线封档，视为未按本册交付。  
6. **迭代 ≠ 同文件抽漂**：人改覆盖/改结构/工厂规则升级可以变；**同一文件字节未变时，自动抽取结果不得漂**（§2.3）。

### 2.3 同材同果（本册「防幻觉」· 硬纪律）

老板口径：**同一份材料前后上传，结果应一致，而不是每次上传每次变。**  
这才是本册说的防幻觉——对准的是**非确定性抽取飘结果**（典型：LLM 温度/采样导致同文不同稿），不是先纠结「哲学上有没有编造」。

对齐 [`llm-determinism.md`](./llm-determinism.md)：抽取属**生成类必须确定性/可复现**；工厂规则版本升级导致「新旧两次不同」要另标，不能假装同一次管道在抽签。

#### 2.3.1 必须稳定的是什么

| 输入不变时 | 必须一致（同材同果） | 允许变（那是迭代，不是飘） |
|------------|----------------------|------------------------------|
| 同一文件内容（建议用内容哈希）+ 同一抽取器版本 | `proposal` 核心：`feature_lines` / `out_scope_lines` / 实现章相关 `sections` / `excerpt` 截取规则结果 | 人手动改过的结构 |
| 同上 | 空抽/弱抽告警是否触发 | 人标的 `coverage` / `status` / 喂助手次数 |
| 同上 | `hits` 仍为空（不跑匹配） | 工厂侧域皮补完后，人对覆盖的**重判** |

**禁止**：同 PDF 今天抽 12 条、明天抽 9 条且内容对不上；同文点两次「重新抽取」得到两套故事（规则版本未升时）。

#### 2.3.2 怎么保证

1. **双轨**：确定性分桶/表题注裁证据包（章节温度 §3.0）→ **LLM 主抽**三栏与覆盖预选（`thesis_absorb_drafts`，`TEMP_ABSOLUTE` + 校验 + 缓存键含版本）；正则只切证据 + **形态钳子**拼装结果，**禁止**正则发明角色/功能，**禁止**为客户遣词/查重改写加正则专线。  
2. **无 LLM**：实体仅表题注；**角色回填合同端名**（`role_hints` / ××端 / 表里已有的用户·管理员等岗名壳）；功能空；覆盖=`unknown`；黄条写明原因（无 Key/关阶段/超预算/调用失败）。禁止旧启发式发明功能清单。详情须能看出「是否用上模型」。  
3. **采样**：走 `temperature_for("thesis_absorb_drafts")`；吸收页**不**挂温控旋钮；改温或改提示须 bump `EXTRACTOR_VERSION` / `PROMPT_ID`。  
4. **内容哈希**：入库记 `content_sha256`（或等价）；同哈希再次上传/重抽 → 期望与库内 `proposal` **字段级一致**（可测）；不一致即红（规则版本 bump 除外，见下）。  
5. **抽取器版本**：记录 `extractor_version`（规则/焦点策略的显式版本号）。仅当版本升级时，允许同哈希重抽得到新结果，并在 UI 提示「抽取规则已升级，结果可能与上次不同」——这是**规则迭代**，不是幻觉飘。  
6. **机器测**：夹同一份固定终稿夹具，连续抽取两次（或上传两次）→ `proposal` 关键字段相等；另测「改一个字节 → 允许不同」。  

#### 2.3.2a 产品硬边界（跟合同，不跟措辞）

| 跟 | 不跟 |
|----|------|
| **合同形态**：角色岗名、功能「××管理」级短名、题注/库表实体 | 某一届论文的句式、口语尾巴、UML「××类」列举腔、查重换写法 |
| **LLM** 读写法差异，抽到同一类要素 | 每撞一种说法就加一条正则 / 词表专线 |
| **钳子**只做形态闸（空壳、岗名剥壳、无题注不进实体、叙述步骤残片） | 把钳子当「读懂论文」的主脑 |

一句话：**客户数据形态（遣词）变了，不更新产品规则；合同形态变了才 bump 版本改钳子/提示。**  

#### 2.3.3 附带仍要守的（假厚 / 假已齐）

同材同果是主约束；下面几条防止「稳定地错」或「用人手/模型把稳定稿毁掉」：

| 项 | 口径 |
|----|------|
| 薄优于假厚 | 空/弱抽告警；**禁止**为消黄而生成无依据行 |
| 覆盖 | LLM 可预选；人可改；**禁止**无 LLM/吃不准时硬标 `covered`；禁止当出包匹配成功 |
| 喂助手稿 | 只序列化当前库内结构 + 固定口令头；禁令句保留 |
| 无「智能补全模块」按钮 | 人可粘贴原文增行，不可一键让模型补清单 |

#### 2.3.4 与 §2.2 怎么共存

- **同材同果**：文件没变、抽取器版本没变 → 自动抽多少次都一样。  
- **可迭代**：人改覆盖/改结构、换文件、或**显式升级** `extractor_version` 后再重抽 → 结果可以变，且要说得清「为什么变」。  
- 禁止把「再点一次碰运气」包装成迭代。

## 3. 抽什么（本科论文读法 · 真源）

> **本科信息系统类终稿**绝大多数是同一壳：封面题 → 摘要背景 → 绪论水 → 技术介绍 →（可行性）→ **需求/用例定角色** → **总体设计各端定功能**（+ 图/表）→ 实现印证 → 测试印证 → 结论致谢文献扔掉。  
> 下面按**标题语义**分块；**禁止写死章号**。口语里说的「三四章」= 需求 + 总体设计，**只帮助理解，不当闸门**。

### 3.0 优先级梯子（写死 · 实现不得改序）

P0～P3 **不是各挖各的孤岛**，而是一张**交叉验证网**：

- **谁先开口**：功能清单以 P1 各端模块（字+图）为准；角色以 P2 需求/用例为准；表以 P1 库表为准；题眼以 P0 为准。  
- **谁来对账**：P2 角色 ↔ P1「××端」；P1 功能 ↔ P1 结构图 ↔ P3 实现入口 ↔ P3 测试用例名；P1 表 ↔ P1/P4 里的业务对象 / E-R。  
- **冲突怎么裁**：高等级有结论时，低等级**不得覆盖**（禁止「实现章填厚」反写设计清单）。低等级多出来的、高等级没有的 → 告警或 `out_scope`，**禁止脑补进必补清单**。  
- **缺一块时**：缺图不挡文字 P1；缺 P3 不挡入库；**缺 P1 各端清单** → 弱抽/失败告警，不得用 P3 顶替。

| 等级 | 名称 | 主产出 | 一句话 |
|------|------|--------|--------|
| **P0** | 题名 | 题眼 | 只要题；与后文系统名交叉（对得上才稳） |
| **P1 · 重点** | 总体设计 · 各端模块（含各端功能结构图） | **功能清单** | 功能主矿；字不准用图；**字↔图必须交叉** |
| **P1 · 重点** | 物理结构 / 库表 | **表与实体硬证据** | 字段、主外键、comment → 将来 SQL；与模块/E-R 交叉 |
| **P2 · 重点** | 需求分析 · 用例（含用例图） | **角色** | 定有几端、叫什么；与设计「××端」交叉；**不是**功能主清单第一来源 |
| **P3 · 次重点** | 系统实现 | 功能/界面**佐证** | 确认设计里的做了；可补入口名；**禁止当主矿**；与 P1 交叉 |
| **P3 · 次重点** | 系统测试 | 功能**验货** | 确认测到了；与 P1/P3 实现交叉；设计/实现皆无的吹点不假交 |
| **P4 · 辅助** | 类图 / 序列图 / 活动图 / E-R 等 | 还原与校验 | 帮 P1/P2 交叉，不单独发明功能 |
| **P5 · 背景** | 摘要 / Abstract | `background` 短摘 | 只介绍背景；**不当**角色/功能/实体源 |
| **P6 · 备用** | 绪论里的「论文主要结构」 | 章节地图 | 与后文标题对账；不当功能行 |
| **P7 · 条件收** | 绪论其它正文 | 偶发「××管理」 | **默认不收**；仅当后文需求或设计有明确对应才收（§3.1） |
| **丢弃** | 目录、技术/工具、可行性、结论、致谢、参考文献、附录大段代码 | — | 不进能力要素；目录行**禁止**当正文裁切锚点 |

**重点** = P1 + P2（缺则吸收算薄/失败告警）。  
**次重点** = P3（交叉验证网的一环；不能独撑清单）。  
**丢弃 / 背景 / 备用** = 不得挤占重点席位。

#### 3.0b 交叉验证（最小集合 · 可测）

| 对账对 | 期望 | 失败时 |
|--------|------|--------|
| P2 角色 ↔ P1「××端 / 角色列举」 | 两端集合大体同构 | 告警「角色与端不一致」；不擅自改名脑补 |
| P1 文字模块清单 ↔ P1 各端结构图 OCR/标签 | 同名或可归一 | 只在一边 → 待确认/告警，不单边升格为必补 |
| P1 功能 ↔ P3 实现小节/入口 | 主路径在实现里能对上 | 设计有实现无 → 告警；实现有设计无 → 不自动进主清单 |
| P1 功能 ↔ P3 测试用例名 | 主功能有测到痕迹 | 测到设计未列的**能力名** → 告警（不假交）；**禁止**把操作步骤撕进 `out_scope` |
| P1 库表 ↔ 模块/E-R 业务对象 | 表能挂上业务名 | 表有模块无 / 模块有表无 → 告警，不删对方 |
| P0 题眼 ↔ 正文系统名 | 业务域一致 | 严重偏离只告警，不以题名改功能清单 |

### 3.0a 分块明细（标题语义 → 动作）

| 等级 | 内容块 | 常见标题词（例） | 工厂动作 |
|------|--------|------------------|----------|
| P0 | 题名 | `…的设计与实现`；`基于 Spring Boot / Vue 的…设计与实现` | **只要题目**；题眼 = 去掉套话后的业务名 |
| 丢弃 | 目录 | 目录、CONTENTS、点线+页码章条 | **整段丢弃**；不得当 `strip` 锚点 |
| P5 | 摘要 / Abstract | 摘要、Abstract | 短摘进 `background`；稳、短、可复读 |
| P7 / P6 | 绪论 / 引言 | 绪论、引言、研究背景/现状/意义、主要工作、论文主要结构 | 默认不收功能；结构小节 → 备用地图；例外 §3.1 |
| 丢弃 | 技术 / 工具 | 相关技术、开发工具、技术及环境、框架介绍 | 丢弃 |
| 丢弃 | 可行性 | 可行性分析、经济/技术/操作可行性 | 丢弃 |
| P2 · 重点 | 需求 / 用例 | 需求分析、功能需求、用例分析、用例图、用例说明 | **定角色**（正文+图） |
| P1 · 重点 | 总体 / 模块设计 | 系统总体设计、系统设计、模块设计、××端功能设计、功能结构 | **功能主矿**（「包含 A管理、B管理…」+ 各端结构图） |
| P1 · 重点 | 物理结构 / 库表 | 数据库设计、逻辑设计、表设计、物理结构 | **表/字段/键/comment** |
| P4 | 设计附图 | 关键类图、序列/时序图、活动图、E-R | 辅助验证，不单开功能 |
| P3 · 次重点 | 实现 | 系统实现、功能实现、界面实现 | 佐证；禁登录/首页壳充数 |
| P3 · 次重点 | 测试 | 系统测试、功能测试、测试用例 | **验货**（属实现交叉）；用例步骤禁止进 `out_scope`；仅能力名对不上 → **告警**，不标「不做」 |
| 丢弃 | 文末 | 结论、总结、展望、致谢、参考文献、附录代码 | 丢掉 |

### 3.1 绪论的唯一例外

绪论**默认不进** `feature_lines` / 补齐建议。

仅当同时满足才可收录某条「××管理 / ××模块」：

1. 绪论正文明确写到该名；且  
2. **后文需求或设计桶有明确对应**（同名或可归一的模块/端功能条目）。

否则不收。对比句 / 「现有系统支持…本系统不做…」→ 他方或不交，规则同旧 §3.0b 精神：**宁缺毋滥，禁止假厚**。

「论文主要结构」：只作**章节地图备用**（对账用），不把「第×章写什么」扩成功能行。

### 3.2 角色 / 功能 / 实体（三分法 · 对齐 §3.0 等级）

补齐建议与将来 `roles` / `features` / `entities` 必须按材料结构来，**禁止行业角色白名单、禁止一题一修词表**。

| 产物 | 主矿（必须按序；高等级压低等级） | 不要 |
|------|----------------------------------|------|
| **角色** | **LLM** 读【P2】（+【P1】××端）；岗名合同形态 | 叙述碎片；把「系统管理员」剥成功能；为「涵盖/即可」加正则专线 |
| **功能** | **LLM** 读【P1】+【P3】/【P4】交叉；稳形态「××管理」；忠于原文有实义才进 | 空壳「系统管理」；口语/UML 类名；用正则穷举查重写法；P3 反写未提及项 |
| **实体 / 表** | **题注/库表**硬证据（正则采题注）+ LLM 补齐短名；题注有的必须进 | 无题注发明过程词；只掐「××管理」词干充数 |

`draft_*` / 入库功能主清单以 **LLM 三栏**为准（正则弱抽仅无 Key 兜底）；角色进 `role_hints` / `draft_roles`；表结构可先落 `sections` 或后续字段，**名字仍跟现网 spec**（§4）。

### 3.3 图与表（默认 PDF · 管道分层）

图是 **P1/P2/P4 交叉验证网的一环**，不是另开一套「看图出包」。默认材料按 **PDF** 想定（Word 先转页或抽嵌图，口径同左）。

#### 3.3a 材料口径

| 材料 | 口径 |
|------|------|
| **各端功能结构图** | 与 P1 文字清单**并列真源**；两边都有才稳；只在一边 → 待确认/告警，不脑补 |
| **用例图** | 服务 P2 角色交叉 |
| **类图 / 序列 / 活动 / E-R** | P4：帮还原与校验，不单开功能 |
| **库表（真表或表截图）** | P1 实体硬证据；字段级才算硬 |
| **实现截图** | P3 佐证界面，不发明设计未列的菜单 |

#### 3.3b 看图管道（实现纪律 · 用库不用自研算法）

**硬纪律：读 PDF 图/表必须走成熟库的现成能力，禁止在厂内自研「抠框 / 连通域 / 自写版面分析」当主路径。**  
工厂只做：选库、接线、题注锚定、与 §3.0b 文字交叉、同材同果测。换库可以，另写一套视觉算法不行。

| 层 | 做什么 | 用库（选型可替换，须是现成库） | LLM？ |
|----|--------|--------------------------------|-------|
| **0 锚点** | 这是哪张图 | 已有正文抽字（题注 `图 4.2…`）；PDF 库按页取文 | **否** |
| **1 出图 / 嵌图** | 得到页图或嵌入图 | **PyMuPDF（fitz）** 等：渲页、`get_images` 导嵌图 | **否** |
| **2a 表** | 库表字段 | **pdfplumber / camelot / tabula** 等抽表；Word 走现有表格读取。扫描表 → 库自带的表检测+OCR 链路，不自写 | **否**（主路径） |
| **2b 结构图文字** | 模块名等标签 | 页图/嵌图 → **PaddleOCR / RapidOCR / Tesseract** 等现成 OCR；需要版面时用库自带 layout，**不自研切框** | **否**（主路径） |
| **3 交叉** | 与文字 P1/P2 对账 | 厂内确定性字符串归一（§3.0b）——这是业务对账，不是视觉算法 | **否** |
| **4 补洞（可选）** | OCR 仍糊 | 同页图 + 题注 + 已有文字词典；视觉模型只读标签且必须落在词典内 | **可关**；不得作默认上传唯一路径 |

纪律：

1. **文字分块按 §3.0 必须先可运营**；图管道未就绪 → 按钮灰并说明，**禁止**因此把 P3 升格成主矿。  
2. **同材同果**：同一 PDF + 同一库版本/参数 + 同一 `extractor_version` → 图侧结果稳定可测；禁止默认「整页丢多模态碰运气」。  
3. 审/对账遵守 [`llm-determinism.md`](./llm-determinism.md)：交叉穷尽后 LLM 只补缺口。  
4. 图注或 OCR 成功 → 写入对应 `sections[].lines`（或 caption），`has_figure_text=true`；不另起平行字段树。  
5. 文档/PR 若出现自研轮廓检测、手写连通域当主路径 → **拒收**，改接库。  

### 3.4 `focus=thesis_impl` 落地纪律

| 项 | 口径 |
|----|------|
| 认块 | **只认标题语义**，禁止「必须第 4 章才是设计」 |
| 加权 | 严格 §3.0：**P1 功能/表 ≫ P2 角色 ≫ P3 佐证**；P5 摘要只背景；P7 绪论默认不进功能 |
| 目录 | 识别后丢弃，且**不得**当 `strip` 裁切锚点 |
| 空/薄 | **P1 无各端清单** → 弱抽告警；**禁止**用 P3 登录项填厚 |
| 同材同果 | 同一正文 + 同一 `extractor_version` → 关键字段相等（§2.3） |
| 重做 | 现网抽取若与本节冲突 → **按本节重写**，禁止叠正则续命 |

### 3.5 题名 / 年份（字段怎么用）

| 用途 | 题名 `title` | 年份 / 届次 |
|------|--------------|-------------|
| 封面抽取 | 优先匹配 `…设计与实现` / `基于…的…设计与实现` | — |
| 厂库存档、列表辨认 | 可存；UI 可折叠或打码 | 可存档侧栏，**不**进喂助手默认稿 |
| 喂助手稿 / 反推开题 | **默认不贴原题名**；用「某业务系统」或人工改写题 | **禁止照搬** |
| 匹配主键 | **禁止**用原题名当命中依据 | — |

### 3.6 不抽进「必须补厂」的

- 目录、技术章、可行性、结论、致谢、参考文献、附录大段代码  
- 某年具体故事（防撞题；可存档对照）  
- 纯格式排版 → 格式参考旁路  
- 本厂明确不交的技术吹点 → `out_scope_lines`，不为跟文做假能力

## 4. 结构化数据（与开题同名同物）

**禁止**另起一套字段名（不要 `AbsorbCard` / `shell` / `capabilities` / `surfaces` / `factory_hint` / `opening_draft_seeds` 这类平行词）。  
论文吸收的正文结构 = 开题已有的 **`proposal` 摘要**（`summarize_proposal` 产出），只换材料角色与 focus，不换字典。

### 4.0 主体：就是 `proposal`

真源形状见 `backend/app/services/proposal.py` → `summarize_proposal`：

| 字段 | 含义（开题 / 论文同一套） |
|------|---------------------------|
| `title` | 题名（存档用；喂助手默认策略见 §3.4） |
| `background` | 背景/意义短摘 |
| `feature_lines` | 功能 / 模块清单（**设计各端为主矿**，§3.2；实现/测试仅佐证） |
| `out_scope_lines` | 范围外 / 不该假交的（开题「非功能·不做」；论文实现章吹了但工厂不交的也进这里） |
| `sections` | `{ heading, lines }` 按标题切的分桶切片（需求/设计/实现/测试/绪论等；图注能读也进对应 `lines`） |
| `hits` | 开题匹配命中词；**论文吸收默认空**，禁止上传瞬间当硬匹配结果填满 |
| `excerpt` | 正文摘录 |
| `char_count` | 字数 |

### 4.0a 材料侧仅多「角色 / focus」（仍用现成词）

分堆上传已有材料 `role`（`proposal` / `taskbook` / `checklist` / `unknown`，见 upload_cluster）。论文加一种角色即可：

| 键 | 取值 | 说明 |
|----|------|------|
| `role` | `thesis` | 与 proposal/taskbook 并列，**不是**新摘要类型 |
| `focus` | `thesis_impl`（论文）/ 开题现网默认 | 同一套切片+`summarize_proposal`，加权段不同 |
| `source_files` | 开题建项已有同名字段 | 文件名列表，不另造 `source` 对象 |

### 4.0b 补厂时才用的项目字段（名字跟 spec 走）

助手补厂或第 2 刀验收若要挂「像项目那样」的提案，**只用现网 spec 已有名**，且论文吸收入库时**默认可空、不算已匹配**：

| 字段 | 现网含义 | 论文吸收 |
|------|----------|----------|
| `roles` | 端角色 | **需求/用例 + 设计各端**（§3.2）；与开题 attach 后同名 |
| `entities` | 实体 | **库表设计优先**；辅以设计业务对象；禁止只掐「××管理」词干充数 |
| `features` | 功能清单（catalog 形） | 由设计各端 `feature_lines` 映射；**不要**另叫 capabilities |
| `domain` / 皮相关键 | 匹配结果 | **上传禁止当硬结果写入**；覆盖判断 / 补厂提案阶段才填（已齐也可记「挂靠域草稿」作回归标签，不算出包匹配） |

反推开题（验收第 1 刀）：直接读 `feature_lines` + `background`（+ 人工改写题，见 §3.4），**不要**再做一份 `opening_draft_seeds`。

### 4.0c 刻意不做

- 禁止第二套摘要 schema / 第二套字段词典。  
- 禁止用 `DOM-*` 当入库主键或必填。  
- 禁止吸收当下跑 match 把 `hits`/`domain` 填成「已匹配」。  
- 禁止把整章原文代替 `excerpt`/`sections` 短结构。

### 4.1 与开题上传的复用边界（防两套逻辑）

开题现网家在 `backend/app/services/proposal.py`（读盘）+ `catalog.proposal_focus_for_match` / `project_match`（匹配）+ `attach_accept`（出包）。  
论文吸收**必须复用前半、禁止复用后半**；**交互栈不要共用**（见 §UI.5）。

| 层 | 开题已有 | 论文吸收 | 纪律 |
|----|----------|----------|------|
| **读文件 → 纯文本** | `read_proposal` / `read_proposal_documents`（txt/docx/doc/pdf） | **直接复用** | 禁止再写第二套 docx/pdf 抽字 |
| **裁噪声** | `strip_non_dev_sections`（参考文献/致谢/进度） | **复用并加固**：目录点线不得当裁切锚；再裁技术章/可行性/结论致谢文献；绪论默认不进功能（§3.1） | 同一 `proposal` 服务；规则进同一家 |
| **捞模块 / 表 / 题名** | `extract_module_lines` / 表抽取 / 题名正则 | **候选可复用**；论文加权以 **设计各端** 为准（§3.0） | 焦点加权可分叉；**抽取主路径按 §3 重做**，禁止旧「全文扫模块」喧宾夺主 |
| **端角色** | 开题侧列举/岗名扫词 | **需求用例 + 设计各端** → `role_hints` / `draft_roles` | **禁止**行业角色白名单；禁止叙述句「…登录」碎片 |
| **补齐建议三分法** | （开题 attach 后同名字段） | `draft_roles` / `draft_entities` / `draft_features` | 严格按 §3.2；升版须重读源文件整抽，禁止只洗库存 JSON 假升版 |
| **章节切片** | 开题用 `_SECTION` 等弱切 | 论文按**标题语义**切分块（§3.0，非死章号） | **共享切片器**，策略参数不同（`focus=opening` / `focus=thesis_impl`） |
| **图 / 库表** | 开题上传基本不吃 | 各端结构图交叉验证；表结构→字段/键/comment | 挂同一材料管道旁路；未就绪不挡文字分块，也**不得**因此改主矿 |
| **匹配 → `DOM-*` → 建项 bake** | `create_from_uploads` / `proposal_match` / `attach_accept` | **禁止走** | 成功态是厂库记录，不是 Project ZIP |
| **摘要对象** | `summarize_proposal` → `spec.proposal` | **同一函数、同一字段**；论文 `role=thesis` + `focus=thesis_impl` 后再 summarize | 禁止平行摘要类型 / 平行字段名 |
| **下游** | 匹配 → 建项 bake | 写入厂库记录（仍持有 `proposal`）；不建出包项目 | 只换下游，不换字典 |
| **分堆弹窗 / 确认创建项目** | Projects 上传 UX | **禁止复用** | 复用停在读盘 API + 可选只读 `proposal` 卡片组件 |

落地时优先：把「读盘 + 裁切 + summarize」收成**一份材料文本管道**；开题与论文只换 **role / focus + 下游**（匹配出包 vs 入库补厂）。

### 4.2 厂库记录（开工必须先定的对象）

「进厂库」不是口号，是**独立于 Project 的材料记录**。一篇终稿 → 一条记录，内挂同一份 `proposal`。

建议字段（名字可跟现网材料/plan 习惯靠，**不要**再发明第二套摘要词典）：

| 键 | 含义 |
|----|------|
| `id` | 记录主键 |
| `role` | 恒 `thesis` |
| `focus` | `thesis_impl` |
| `source_files` | 源文件名列表 |
| `proposal` | §4.0 同名对象 |
| `status` | `extracting` / `review` / `stored` / `fed` / `covered` / `patched`——**当前标签，可回退**（见 §2.2），不是封档枚举 |
| `coverage` | `unknown` / `covered` / `skin_gap` / `domain_gap`；默认可改，**不是** match 结果 |
| `extract_round` | 整数，从 1 起；每次重抽 +1（同哈希同版本时 `proposal` 应与上轮相同） |
| `content_sha256` | 源材料内容哈希；同材同果对账键 |
| `extractor_version` | 抽取规则/焦点策略版本；仅 bump 时允许同哈希结果变化 |
| `has_figure_text` | 派生布尔 |
| `draft_roles` / `draft_entities` / `draft_features` | 补齐建议三栏（LLM 主抽） |
| `draft_schema_sql` | 论文物理表 → 可核对 MySQL DDL（空串=未抽出；**落库**；不进 ZIP） |
| `schema_extract_meta` | 题注数/有列数/跳过表/warnings/homology_ok |
| `created_at` / `updated_at` | 时间；任何重抽/改结构/改覆盖都碰 `updated_at` |

**禁止**：用 Project 行冒充吸收记录；吸收成功态去写 `projects` 表或触发 bake。  
**禁止**：同文件同版本两次抽取结果漂移（§2.3）。  
**禁止**：把首次 `covered` 当成永久真理（一刻不当永久 ≠ 抽取可飘）。  
`coverage=covered` 仍保留厂库记录，便于以后当**可再跑**的回归样本。

### 4.3 跨篇去重

粒度仍是 `feature_lines` / `out_scope_lines` 字符串归一，**不**另发明 `dedupe_key` 体系。

纪律：

- **禁止**入库时静默并集改已有开题种子或他篇记录。  
- 高重叠 → 详情顶提示「与 #id 重叠 N 条」，提供「查看对照 / 仍单独保留」。  
- 真要合并 → **人工勾选**后再并；冲突列表可见。  
- 产品至少：**重叠提示 + 查看对照 + 仍单独保留**；静默并集仍禁止。合并勾选可与提示同刀或紧随，不得整段缺席还称已齐。

## 5. 喂助手怎么干

人把厂库里的结构化结果交给助手时，**先按 §2.1 覆盖判断选口令**，不是一律「开新域」：

| `coverage` | 助手默认任务 |
|------------|----------------|
| `covered`（已齐） | **验证 / 回归**：确认主路径已能交；可协助第 2 刀试跑；**禁止**无缺口仍新开域或平行旁路；可把本记录标成回归样本 |
| `skin_gap`（差皮） | **只补皮**：rules / pack / seed 同到；扫易混对；标 gap 册 |
| `domain_gap`（差域/能力） | **挂 cap 或薄开 DOM-***；按 onboarding；禁止只擦 ZIP |
| `unknown` | 先做覆盖判断，再选上行；拿不准按有缺口审 |

共同纪律：

1. 扫同类面，写入共享机制 + 测试；标 [`domain-skin-gap-analysis.md`](./domain-skin-gap-analysis.md)。  
2. **不**用该结构直接对学生包出 ZIP 当交货；出包仍走「开题/材料 → 匹配 → bake」。

### 5.1 导出物（产品面，不是口头）

控制台「复制喂助手稿」一次给出固定形状（无此截 = 入口假功能）：

1. **口令头**（按覆盖分支，定死一种）：  
   - 已齐：`验证工厂已覆盖；勿新开域；可协助第 2 刀回归；本稿来自终稿吸收，不是出包订单`  
   - 差皮：`修工厂·只补皮；能皮就皮；禁止只擦 ZIP；本稿来自终稿吸收`  
   - 差域：`修工厂·挂 cap 或薄开 DOM；禁止平行旁路与只擦 ZIP；本稿来自终稿吸收`  
   - 未知：`先做覆盖判断（已齐/差皮/差域），再动手；本稿来自终稿吸收`  
2. **结构正文**：`proposal` 的 Markdown 或 JSON（`feature_lines` / `out_scope_lines` / 实现章 `sections` 为主；默认不含原题名与届次，见 §3.4）。  
3. **指针**：写明对照 [`domain-skin-onboarding.md`](./domain-skin-onboarding.md)、[`domain-skin-gap-analysis.md`](./domain-skin-gap-analysis.md)（文件名即可，勿贴整册）。

复制成功后可将记录 `status` → `fed`（可再次复制，不锁）。人可再标：`covered` / `patched`；之后仍可重抽、改覆盖、再喂（§2.2）。  
口令头与结构正文**永远按点击当下的库内当前值**拼，不缓存「上一次典礼稿」当唯一真源。  
稿末固定禁令句（防幻觉）：`不得发明下列未出现的能力；不得将本稿当作已匹配出包；不交项见 out_scope，禁止假交。`

## 6. 验收（两刀）

| 刀 | 问什么 | 红了怎么办 |
|----|--------|------------|
| **1 开题可还原** | 只看结构化结果，能否写出一篇像任务书的开题（角色、流程、模块齐全） | 先改抽取 / 补抽，再谈补厂 |
| **2 程序可对齐**（**可选**；**已齐时反而更该做**） | 用反推开题走**现网**匹配 + bake，演示**主路径**是否与论文实现章一致 | 红了 → 覆盖判断可能错了，改判差皮/差域再补；不是否定论文 |

说明：

- 第 1 刀查抽取质量；第 2 刀查「现厂是否真盖住」。  
- **已齐**：第 2 刀是主验收（证明不用补厂）。**有缺口**：补完再砍第 2 刀。  
- 对齐看**可演示主路径**；格式章节对不齐不算本册红灯。  
- 任一条红 → 改抽取或补厂落点，**禁止只擦单包**。

### 6.1 防绕回：第 2 刀不是出包捷径

- 第 2 刀**默认收起**；吸收详情页**禁止**内嵌 MatchTab /「确认创建项目」/ 出包进度。  
- 若做按钮：文案为「用反推开题去项目页试跑」→ 下载/预填 txt 后**跳转 `/projects`**，二次确认写明「这是验收，不是本单交货」。  
- 试跑产生的 Project 与吸收记录**解耦**（可记可选 `trial_project_id`，不把吸收成功态绑在 ZIP 上）。  
- **禁止**把「生成开题 → 匹配 → bake」做成吸收页默认主路径。

## 8. 控制台 UI（定稿）

### 8.0 三条硬隔离

| 现网 | 终稿吸收必须 |
|------|----------------|
| `/projects` 上传 → 分堆 → **确认创建项目** | **禁止**同页同按钮；独立路由 |
| 项目详情「产物 → 论文材料」 | 侧栏/面包屑**不得**叫「论文材料」；用 **终稿吸收** / **论文进厂** |
| MatchTab 匹配确认 / 能力勾选 | 吸收详情**无**「采纳匹配 / 生成工程」 |

### 8.1 信息架构

- **侧栏**：挂「资产台」下（与词表 / 能力说明同类「补厂资产」），**不要**塞「工作台 → 项目」。  
  - 标签：`终稿吸收`  
  - 副文：`抽需求·设计·实现进厂库，不建项`  
- **路由**：`/thesis-absorb`（列表）+ `/thesis-absorb/:id`（详情）。  
- **Help**：单独词条：上传开题出包 / 终稿吸收（已齐也吸）/ 产物论文图；覆盖三态；按标题分桶非死章号（§3.0）。

### 8.2 列表页

1. 顶栏一句：**从终稿（需求/设计/实现等）抽出可交要素入库；对照现厂看已齐或缺口；不会创建项目、不会出 ZIP。**  
2. 上传区：单篇 PDF/Word/TXT 为主；**不要** 8 份分堆、不要「生成测试开题」入口。  
3. 表列：入库时间、题名（可折叠/打码）、文字/含图注、`feature_lines` 条数、**覆盖**（未知/已齐/差皮/差域）、`status`、操作（打开 / 复制喂助手稿）。  
4. **禁止**行内「去匹配」「创建项目」。

### 8.3 详情页（自上而下）

| 区 | 内容 | 禁止 |
|----|------|------|
| **身份条** | `role=thesis`、focus、源文件、字数、是否含图注 | 显示 `hits` 当出包已匹配 |
| **结构审阅** | `feature_lines`、`out_scope_lines`、分桶 `sections`、短 `excerpt`；绪论对账告警若有 | 整章原文墙；空模块仍标成功 |
| **覆盖判断** | 三选一：已齐 / 差皮 / 差域（+ 可选挂靠域草稿、缺口短注）；文案「对照现厂，非出包匹配」 | 上传自动写成匹配成功；已齐时仍诱导向「开新域」 |
| **补厂线索（可空）** | `roles`/`entities`/`features` 草稿；已齐可空 | 当出包 spec 用 |
| **喂助手** | 按 `coverage` 复制 §5.1 对应口令头 | 「一键 bake」「一键建项」 |
| **验收** | 已齐：第 2 刀可默认展开；有缺口：补完再验；第 1 刀始终可看反推开题 | 本页内嵌 MatchTab / 出包进度 |

空态：`feature_lines` 过少 → 黄条先改抽取；覆盖未选 → 喂助手稿走「未知」口令头。

### 8.4 文案词表（控制台定死）

| 场景 | 用 | 禁用 |
|------|----|------|
| 页标题 | 终稿吸收 / 论文进厂 | 上传论文出包、智能匹配论文 |
| 成功入库 | 已写入厂库，请做覆盖判断后复制喂助手稿 | 已创建项目、匹配成功、可下载 ZIP |
| 已齐 | 现厂已盖住主路径；可回归验证，不必新开域 | 匹配成功请出包 |
| 按钮 | 入库、重新抽取、改结构、改覆盖、再复制喂助手稿、标记已齐/已补厂（均可反复） | 确认创建、开始生成、预览学生端、一次性封档只读 |
| 进度 | 正在按章节标题抽取 | 正在解析并分堆 |
| 与产物区 | Help 写清「产物·论文材料 ≠ 本页」 | 两侧都叫「论文材料」 |

### 8.5 与开题上传的交互复用

| 可借 | 不可借 |
|------|--------|
| 选文件组件、解析进度条、只读 `proposal` 字段卡片 | 分堆弹窗、`确认创建 N 个项目`、上传任务「查看分堆」、MatchTab 整页 |

### 8.6 去重 / 图（UI）

- 重叠提示见 §4.3（提示 + 对照 + 仍保留；禁止静默并）。

### 8.7 产品交付清单（口令 `做论文吸收` · **不是 MVP**）

下令实现时按**可运营的完整产品功能**收工，禁止「先做一个上传壳再说明二期」。缺任一项不得称本能力已交。

| # | 必须交付 | 验收要点 |
|---|----------|----------|
| P1 | 厂库表 + API | §4.2 字段齐；不建 Project；CRUD/上传/重抽 |
| P2 | `thesis_impl` 分块抽取 | **按 §3 重做**：设计各端主矿、需求定角色、实现/测试佐证；目录/技术/可行性/文末丢弃；图文交叉；表结构→SQL；弱抽告警；禁脑补；禁死章号；**旧启发式作废** |
| P3 | 同材同果 | §2.3：`content_sha256`、`extractor_version`、双次抽取相等测、默认禁 LLM 抽行 |
| P4 | 侧栏 + `/thesis-absorb` 列表/详情 | §8.1～8.4 文案与隔离；无匹配/建项/出包主按钮 |

| P6 | 喂助手稿 | §5.1 四覆盖口令头 + 结构正文 + 禁令句；只读库 |
| P7 | 覆盖三态 UI | §2.1；默认 `unknown`；人可改 |
| P8 | 验收两刀 UI | 第 1 刀反推开题预览；第 2 刀「去项目页试跑」+ 二次确认（§6.1），与吸收记录解耦 |
| P9 | 跨篇重叠提示 | §4.3 至少提示+对照+仍保留 |
| P10 | Help | 三「论文」词对比 + 覆盖三态 + 同材同果一句 |
| P11 | 测试 | 入库形状、空抽告警、同材同果、不触发 match/建项；关键文案禁词 |

**诚实边界（仍算产品齐，不是 MVP 借口）**：

- **不出包、上传不硬匹配**——产品设计如此，不是少做。  
- **图补抽**：管道未就绪可灰按钮并写明；文字路径 P1～P11 仍必须齐。  
- **抽取历史表**：可不做多版本留痕；当前稿 + `extract_round` + 同材同果即可。

做成半截入口 / 不能迭代 / 同文件两次结果飘 / 无喂助手稿 → **未按本册交付**。
