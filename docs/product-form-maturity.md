## 1. 内部工具 vs 产品化应用

即使仅本人使用，仍按**产品化应用**标准建设——否则长期停留在「高技能操作者依赖型内部工具」。

| | **内部工具**（现状偏此） | **产品化应用**（目标） |
|---|----|----|
| 正确性由谁保证 | 操作者记得刷新时机、重生成时机、去哪个页 | **交付就绪指示 + 门禁**保证；人只做匹配确认与例外裁决 |
| 写操作成功的 UI 表现 | HTTP 200，界面仍可能 loading 或旧数据 | **乐观更新**；随后异步对齐服务端；对齐失败不否定写成功 |
| 常规订单 | 常开修复会话 / 热修复复现 | **人工介入率 → 0**；缺陷进共享机制 + 自动化检查 |
| 能力边界 | 内部文档清楚，对外表述含糊 | **能力目录 = 已交付 ∪ 不支持**；功能待办不进对外承诺 |
| 材料 | ZIP 可交，论文图/PPT 另线跟 | 程序 ≈ README ≈ 论文「系统实现」≈ 答辩材料（仅余查重） |
| 发布 | 工作副本已改、主线未合入可长期存在 | **发布火车**：可回溯版本 = 运行中实例行为 |
| 预览容量 | 本机资源够用即可 | **资源配额** + 拒绝原因说明（或文档写明 single-operator 定位） |
| 主导航 | 多 Tab 并列、依赖经验 | **向导式主路径** + 唯一 **主操作**：清洗 → 验圈 → 合卷 → 下载 |

**目标一句话**：日常使用时依赖状态机与校验，而不是操作者记忆与人工介入。

**对标声明（2026-11-06）**：「好不好用 / 跟不跟手」的合格线 = **软件公司交付的 B 端产品级运营控制台**（阶段机 + 唯一主操作 + 可恢复错误），**不是**「作者本人小团队内部工具够用」。单人使用也按产品级标准改交互。

## 2. 评审结论（2026-11-05 · 交互补评 2026-11-06）

### 2.1 总判

- **不是**成熟的对外多租户 SaaS。  
- **是**领域模型深、交付流水线硬、**运营控制台仍偏专家工作台 / 内部工具**的专用生成系统。  
- 对标「常规订单无人值守、控制台行为可信」≈ **70～75%**。  
- 对标「可交付给陌生团队、无需作者在场」≈ **45～55%**。  
- 对标「软件公司 B 端运营控制台交互」≈ **约 2.5～3.0 / 5**（见 §2.4）：队列层尚可，项目详情层明显偏差。

### 2.2 分维（满分 5 · 严格）

| 维度 | 分 | 一句话 |
|------|----|--------|
| 领域交付正确性（ZIP 可答辩） | 4.2 | 主路径与门禁硬；长尾复现用例仍暴露缺陷 |
| 能力边界诚实（拒收 / 双显 / 不冒充） | 4.5 | 边界清晰；AI 能力 B 类与硬件类拒收清楚 |
| 自动化与防回归（学生包） | 4.0 | 门禁与批次强；**控制台写后 UI 契约弱** |
| 运营控制台体验与状态可信 | 2.5～2.8 | 写后同步在修；**信息架构仍偏专家工作台**（§2.4） |
| 论文与答辩材料闭环 | 2.5～3.0 | 图仍在修；答辩 PPT 后端未完成 |
| 规模化运营（预览 / 发布 / 多操作者） | 2.0 | 单机内部工具模型 |
| 文档与交接 | 4.3 | 强；同时暴露工作副本长期未合入 |
| **综合 · 内部交付系统** | ~3.6 | 流水线强，控制台产品化弱 |
| **综合 · 软件公司级产品体验** | ~2.5 | 缺产品级主路径、包装与无人值守 |

### 2.3 已达标项（须保持）

1. **价值主张清晰**：材料 → 匹配 → bake → 门禁 → ZIP；演示级边界诚实。  
2. **交付校验成体系**：空壳禁下载、布局/控件门禁、开题对齐、假宣称硬闸、角色边界、薄壳 + 能力开关。  
3. **能力有台账**：68 域、分组加厚、Path B 拒收、技术栈双显。  
4. **工程文档完整**：docs / HANDOFF / parked / invariants / 审计规则。  
5. **缺陷归属正确**：修共享生成与门禁，禁止只改当前学生 ZIP；用复现用例驱动共享修复。

### 2.4 运营控制台交互评审（产品级 · 2026-11-06）

**合格问题**：界面是否达到**软件公司开发的 B 端运营/履约产品**水准？  
**不合格对照**：作者肌肉记忆下「够用」、小团队内部工具「能出单」。

#### 2.4.1 产品级运营控制台的最低标准

| # | 标准 | 说明 |
|---|------|------|
| 1 | 阶段机可见 | 订单/项目处于哪一阶段一目了然；未完成阶段不可跳步冒充完成 |
| 2 | 主操作唯一 | 每一阶段视觉与文案上只有一个强调按钮（primary action） |
| 3 | 阻断可恢复 | 不能下载/不能前进时：原因 ≤3 条 + 明确下一步 |
| 4 | 渐进披露 | 排障、高级配置、低频工具默认折叠或不与主路径同级 |
| 5 | 成功路径短 | 常规「确认 → 生成 → 质检 → 下载」有效主点击宜 ≤3～5（不含等待） |
| 6 | 写后状态可信 | 操作成功后 UI 立即反映终态（见 §4·A） |
| 7 | 队列驱动 | 工作台列出今日待处理队列，而非先钻进单个项目再回忆 |

#### 2.4.2 现状分层

| 层 | 评价 | 依据（代码/结构） |
|----|------|-------------------|
| **工作台 / 项目列表** | **部分达标** | `OpsHome`：待匹配、生成中、复审、失败类型；项目页上传分堆、履约筛选、页头下载/发出 |
| **项目详情** | **未达标（专家工作台）** | 一级 Tab 并列：匹配 / 一键生成 / 运行 / 日志 / 产物 / 微调；交付质检藏在「产物」二级（数据库 / 论文 / API / 交付复审 / 质量检查 / PPT） |
| **匹配确认** | **偏配置台** | 推荐与解锁、技术栈、视觉表面、多勾选同屏；缺默认「只确认主项」层级 |
| **质检交付** | **路径靠记忆** | 清洗 → 验收轮次 → 重打包 → 下载分散；无常驻交付就绪指示 |

#### 2.4.3 角色体感（非分数，供验收对照）

| 角色 | 是否达到产品级 |
|------|----------------|
| 作者、路径已熟练 | 能出单；**不能**当作产品合格 |
| 另一名运营、只看界面 | 易卡在二级 Tab / 匹配过重 / 不知当前主操作 |
| 软件公司 B 端履约台对标 | **明显偏差**：详情层像 IDE，不像订单状态机 |

#### 2.4.4 改进原则（改 UI 时）

1. **队列层保持并加强**（可下载未发、门禁失败等队列）。  
2. **详情层改为向导式主路径**；运行 / 日志 / 微调 / 论文图进入「工具」或折叠。  
3. **质检交付单页化**：门禁结果、验收轮次、重打包、下载同一工作区。  
4. **匹配页渐进披露**：默认域 / 骨架 / 主路径 / 必勾 / 确认；其余进高级。  
5. **不与「用语 O」混为一谈**：交互信息架构可先改；文案标准名可并行或稍后。  
6. **实现入口**：§4·**P**（本评细项）+ §4·**A/B/I/K**（重叠项合并收口，禁止平行做两套）。

## 3. 产品化原则（改动时必守）

1. **缺陷进共享路径**：`ensure_*` / 门禁 / 基线 / 测试；禁止只改当面 ZIP。  
2. **写成功即更新客户端状态**：先乐观更新，再轻量拉取服务端；busy 不绑定全量 `load`。  
3. **能力目录诚实**：功能待办不进 README「已覆盖」；未实现的技术选项不展示或禁用。  
4. **单一交付就绪叙事**：未就绪 / 可验收 / 可重打包 / 可下载。  
5. **运行中实例 = 已发布主线**：热修复超过一个工作班次必须合入版本控制。  
6. **无人值守可度量**：人工介入率、canary、重打包一次成功率；不靠体感。  
7. **交互对标软件公司产品**：不以「作者觉得跟手」关闭体验项；以 §2.4.1 七条为验收。  
8. **实现必须落在已有路径（极重要）**——见 **§3.1**。产品化波次改的是**编排与呈现**，不是另造一套业务/状态机。

### 3.1 已有实现 · 禁止第二套 · 改前改后逻辑不变（极重要）

产品化（含 §4·A/P/B 运营控制台）落地时，下列三条**同时**满足，缺一不可。与 `cross-domain-fix` / `capability-home` / `boss-intent` 同向；冲突时以本条收紧为准。

| # | 硬约束 | 含义 | 反例（禁止） |
|---|--------|------|--------------|
| 1 | **先搜已有家，只改原路径** | 写前必须搜到现有实现（如 `applyDeliveryReviewPanel`、`refreshDeliveryReviewPanel`、`canDownload` / `download_blocked_reason`、`usePdRuntime`、`OpsHome` 队列、`patchMatch` 回写 `p.value`、门禁/复审 API）。能改原函数/原组件/原字段就改那里。 | 再写一套 `DeliveryStatusStore`、第二套「就绪」计算、平行 `loadProjectLite2` |
| 2 | **禁止第二套逻辑** | 同一职责只保留一条因果链。UI 重组（Tab→阶段、单页拼装）= **搬接与显隐**，不复制判定、不双写状态。 | 顶栏一套 `ready`、质量检查页另一套 `zip_ready`；乐观更新与全量 `load` 两套真相抢同一按钮 |
| 3 | **改前改后业务逻辑不变** | 同一输入（项目状态、门禁、复审轮次、写接口响应）→ **同一输出**（能否下载、能否重打包、阻断文案语义、API 调用顺序与结果处理）。变的是信息架构与主操作呈现，不是规则本身。 | 为「好点」放宽/收紧下载条件；跳过验收轮次；合卷成功条件与后端不一致 |
| 4 | **要改逻辑须先问作者** | 一旦发现**不得不**改判定/条件/API 语义/状态机（而非纯搬接显隐），**停手提问**，取得明确同意后再动代码。禁止「先改再汇报」。 | 未请示就改 `canDownload`、门禁键、复审通过条件、匹配确认语义 |

**何谓「改逻辑」（须先问）**

- 下载/重打包/验收/匹配确认的**可否条件**或阻断原因语义变化  
- 新增/删除/合并门禁键、复审状态、交付标记含义  
- API 请求/响应契约或调用时机导致结果不同  
- bake / 匹配 / 学生包行为变化  

**何谓「不改逻辑」（可直接做，仍守 1～3）**

- Tab/阶段布局、默认落地页、按钮主次与文案呈现（语义不变）  
- 复用已有 computed / `apply*` 做就绪指示拼装  
- 写后乐观更新收口（与已有「响应体 patch → 轻量拉」同模式，不改变服务端规则）

**允许做什么**

- 把已有块拼到新布局（就绪指示复用现有 computed / `apply*`）。  
- 调整 Tab 显隐、默认落地页、按钮主次样式。  
- 写后路径：继续「响应体 patch → 轻量权威拉」——这是**收口已有模式**，不是新状态机。

**禁止做什么**

- 为产品化新建平行 API、平行门禁键、平行「交付状态」枚举（除非册内立项且迁移掉旧路径）。  
- 「先做新的再删旧的」长期双轨。  
- 借交互改动改匹配/bake/门禁语义或学生包行为。  
- **未问作者就改业务逻辑**（见上表 #4）。

**收工自检（每波必答，写入 HANDOFF）**

1. 改的是哪条**已有**函数/组件/字段？（路径列表）  
2. 有无第二套同职责逻辑？（无 / 有则未完成）  
3. 改前改后：下载可否、阻断原因、复审/重打包条件是否仍与改前一致？（抽测或对照）  
4. 本波是否触及逻辑变更？若是，是否已获作者同意？（未问则未完成）

## 4. 改进项全表

### A. 运营控制台状态一致性 · **P0**

**目标**：操作结果立即反映在 UI；loading 仅表示该请求未返回，不表示「可能已成功但界面未知」。

| # | 项 | 现状 | 动作 | 完成定义 |
|---|-----|------|------|----------|
| A1 | 写后客户端状态契约 | 合卷/验圈/清洗等已开始乐观更新；可能仍有遗漏 | 扫 `frontend/src`：禁止「成功 = await 全量 load」；统一写后 patch + 轻量 refresh；refresh 失败不计入写失败 | 清单清零；合卷「未同步」提示在 HTTP 200 后立即消失 |
| A2 | 按钮 loading 生命周期 | 部分仍等重请求结束才清除 | loading 仅覆盖写请求；权威拉取放在 finally 之后或后台 | 写请求返回后 ≤300ms 可再次点击（防重复提交用短锁） |

## 6. 成熟度复测

每季或重大发版更新 §2.2 分数与完成定义勾选，不另起文档。

| 检查 | 通过标准 |
|------|----------|
| 写后状态 | 写成功后 ≤1s 内 UI 反映终态；loading 不挂死 |
| 交付就绪指示 | 不熟悉者可完成下载或看到明确阻断原因 |
| 产品级主路径（§2.4） | 陌生人走查通过；日常交付不依赖产物二级 Tab 记忆 |
| 人工介入率 | 近 30 天低于自定阈值（建议先 20%，再 10%） |
| 运行中实例 = 主线 | 无超过一周、已被运行依赖却未提交的主题 |
| 材料 | 目标图可打开；若宣称 PPT 已交付则无 mock |
| 能力目录 | README/状态列无「功能待办当作已交付」 |
| 预览 | 超限有说明；或文档写明 single-operator 且与实现一致 |

**内部产品化达标建议**：运营控制台体验 ≥4.0、材料 ≥3.5、综合（内部交付系统）≥4.0；其中体验分须含 §2.4 产品级标准，不得用「作者熟练」抬分。
